# SQL conventions

Read this before touching the database. Why the database is shaped this way is in `docs/adr/0005-curriculums-as-revisions-on-neon.md`.

- Use Drizzle ORM with Postgres on Neon, through the `@neondatabase/serverless` driver.
- Avoid raw SQL; use Drizzle's query builder.
- Use Drizzle's relational queries v2 (`defineRelations`), declared in one relations file next to the schema.
- Keep queries atomic and single-purpose: one query, one purpose.
- Put queries in a `queries/` folder under `src/server/db/`, one file per topic, such as `queries/revisions.ts`, and schemas in a `schema/` folder beside it, one file per topic.
- **Table names:** singular and in `snake_case`, matching the entity in `GLOSSARY.md`: `institution`, `program`, `curriculum`, `revision`, `proposal`. Inherently plural or compound tables, such as settings, are the exception.
- **Primary keys:** prefixed nanoid strings, such as `rev_…` for a revision, generated by `pk()` in `src/server/db/columns.ts`. They are public: they appear in URLs and in trajectories.
- **Relations:** name `one()` relations in singular (`revision.curriculum`) and `many()` relations in plural (`curriculum.revisions`).
- **Revisions are immutable.** No query updates or deletes a row of `revision`; a change inserts a new revision and moves the curriculum's current revision.
- **Projections are disposable.** Tables derived from current revisions, such as the courses of an institution, can be dropped and rebuilt, so no feature writes to them directly.
- **Migrations:** generate them with `bun run db:generate` and apply them with `bun run db:migrate`; never edit a migration that has been applied in production.
- **Cost:** reads that visitors trigger go through Next.js caching, so the free plan of Neon is enough (ADR 0005). A query that runs on every visit without a cache needs a reason.
